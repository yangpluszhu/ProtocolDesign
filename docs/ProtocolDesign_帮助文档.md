软件制作方：上海中医药大学附属龙华医院临床研究中心  
作者联系方式：Email: yangpluszhu@sina.com  
GitHub：https://github.com/yangpluszhu

## 软件用途

临床研究方案辅助构建系统（ProtocolDesign）用于将研究团队提供的回顾性队列研究方案摘要，自动扩写为结构完整、格式规范的中文回顾性队列研究方案 DOCX 文档。软件内置 cohort-protocol 技能规则、模板写作指南和 `corhortCRU-small.docx` 版式模板。

## 风险提示

请注意：本方案由AI工具辅助生成，仅供研究团队参考，不应被视为最终结论或决策依据。AI生成内容可能存在事实不准确、逻辑推断不充分、引用来源不完整或过时、对特定研究场景理解偏差等风险，也可能遗漏关键变量、伦理合规要求、数据安全与知识产权风险。研究团队在采纳前应结合专业判断，对方案中的研究假设、技术路线、数据来源、试验设计、合规要求及可行性进行逐项核验，并由相关领域专家进行审查确认。任何基于本方案开展的研究、申报或实施工作，均应以人工复核和正式论证结果为准，软件制作方不对由该软件生成的结果产生的任何不良结果负责。

## 使用步骤

新版界面采用“分组工作台”布局：上方滚动区域按 **步骤 1｜输入摘要**、**步骤 2｜模型配置**、**步骤 3｜输出设置** 分组展示；下方固定区域始终显示操作按钮、进度条和“运行状态与完成简报”日志。

1. 双击 `ProtocolDesign.exe` 启动软件。
2. 在 **步骤 1｜输入摘要** 中选择功能模块：当前版本请选择 `回顾性队列研究方案`。其他 5 个模块为待开发预留。
3. 在 **步骤 1｜输入摘要** 的“方案摘要文档”处选择输入文件，支持 `.docx`、`.md`、`.txt`。
4. 在 **步骤 2｜模型配置** 中选择大模型类型：`deepseek`、`kimi`、`GLM`、`mimo` 或 `自定义`。
5. 若选择 `自定义`，请在 **步骤 2｜模型配置** 中自行填写 OpenAI 兼容的 `base_url`、`api_key` 和模型名称。
6. 填写 OpenAI 兼容接口信息：
   - `base_url`：例如以 `/v1` 或兼容路径结尾的接口地址。
     - MiMo 会自动填入：`https://api.xiaomimimo.com/v1`。
   - `api_key`：对应平台的 API 密钥。
   - `模型名称`：可从下拉框选择常见模型，也可手动输入平台实际可用的模型名。
   - `思考模式`：DeepSeek、GLM、MiMo 默认启用思考/推理模式并请求最大强度；Kimi 按当前版本要求禁用思考模式。
   - `内容长度`：软件会通过提示工程要求模型参照方案模板示例的写作风格和写作要点尽量详尽撰写，整体中文字符数建议不少于 10000 个，但不作为输出阻断条件。
   - `本地保存 api_key`：由用户自行勾选。勾选后，软件使用 Windows 当前用户 DPAPI 加密保存；不勾选则每次运行都需要重新输入。
7. 在 **步骤 3｜输出设置** 中选择输出目录，并填写输出文件名。未写 `.docx` 后缀时，软件会自动补齐。
8. 使用界面下方固定操作区中的“确定生成方案”按钮开始生成，等待模型生成和 DOCX 渲染完成。
9. 完成后，软件会在指定目录生成：
   - 完整研究方案 DOCX 文件。
   - 同名的 `_运行简报.txt` 文件。
   - 若生成失败，程序目录会额外写出 `ProtocolDesign_error.log` 供排查。

## 适用范围

目前版本仅开发了“回顾性队列研究方案”模块，仅适用于回顾性队列研究的方案设计与撰写。其他 5 个模块为后续升级预留，当前不可用于正式生成。

## 输入文档建议

摘要文档越具体，输出方案越稳定。建议摘要中至少包含：

- 研究题目、研究中心或数据来源。
- 研究目的与拟回答的核心问题。
- 目标人群、纳入标准、排除标准。
- 暴露因素、对照组、索引日期或 time zero。
- 主要结局、次要结局、安全性结局。
- 基线协变量、亚组变量、随访与删失规则。
- 统计分析思路、伦理与数据安全要求。

## 模型接口说明

软件调用的是 OpenAI 兼容的 `chat/completions` 接口。若 `base_url` 填写为 `https://example.com/v1`，软件会自动请求：

```text
https://example.com/v1/chat/completions
```

如果服务商要求完整地址，也可以直接填写以 `/chat/completions` 结尾的地址。

内置模型候选包括：

- GLM：`glm-4.5`、`glm-4.5-air`、`glm-4.7`、`glm-4.7-flash`、`glm-5`、`glm-5.1`、`glm-5-turbo`。
- MiMo：`mimo-v2.5-pro`、`mimo-v2.5`、`mimo-v2-pro`、`mimo-v2-omni`、`mimo-v2-flash`。若 MiMo 返回的 JSON 字符串中包含未转义换行、制表符等控制字符，软件会自动修复后解析；如仍无法解析，会自动按严格 JSON 要求重试一次。
- Kimi：`kimi-k2.6`、`kimi-k2.5`、`kimi-k2-thinking`、`kimi-k2-thinking-turbo`。软件会对 Kimi 请求自动使用 `temperature=0.6`、禁用思考模式，并设置较大的输出 token 预算；为避免长方案 JSON 一次性输出时被截断，Kimi 会采用“封面摘要 + 章节分批生成 + 软件本地组装”的专用流程。Kimi 流式响应会强制按 UTF-8 解码，避免中文乱码；封面摘要阶段如未返回最终方案正文，软件会继续尝试 JSON 模式和非流式禁用思考模式；章节分批阶段会继续尝试非流式禁用思考模式；如遇到 `engine_overloaded` 或类似 429 临时过载错误，软件会自动等待并重试；如某个片段出现字符串未闭合、JSON 语法不完整或章节缺失，软件只重试当前片段。

## api_key 本地保存与安全

软件默认不强制保存 api_key。勾选“本地保存 api_key”后，软件会按当前模型提供商分别保存密钥，保存位置为：

```text
%APPDATA%\ProtocolDesign\settings.json
```

该文件中保存的是 Windows DPAPI 加密后的密文，不是明文 api_key。密文通常只能由当前 Windows 登录用户在当前电脑上解密。取消勾选后，软件会删除当前提供商对应的本地保存项。运行简报、错误日志和帮助文档不会记录 api_key。

## 输出内容

生成的 DOCX 默认包含：

- 方案封面。
- 可更新目录。
- 结构化方案摘要表。
- 研究背景、目的、设计、对象、暴露、对照、结局、协变量、统计分析、数据管理、伦理考量。
- 附表 1：暴露、对照、结局与协变量操作性定义总表。
- 附表 2：敏感性分析矩阵。

为了保证方案内容完整详尽，软件会在提示词中要求模型尽量写出不少于 10000 个中文字符的完整方案，并重点展开研究背景、操作性定义、统计分析、数据管理、伦理合规、质量控制和敏感性分析。该长度要求仅作为生成目标，不作为输出限制；即使最终文档未达到 10000 个中文字符，软件也会放行输出。

## 常见问题

如果提示“模型接口返回错误”，请检查 `base_url`、`api_key`、模型名和账号额度。  
如果 Kimi 返回 `engine_overloaded` 或 429 临时过载错误，软件会自动重试；若多次重试后仍失败，请稍后再试或临时切换模型。  
如果 MiMo 返回 JSON 但解析失败，软件会优先自动修复字符串中的未转义控制字符；仍失败时会自动重试一次严格 JSON 生成。  
如果输出文档出现中文乱码，通常是模型接口响应编码被错误识别；软件已对流式响应强制使用 UTF-8，并对明显乱码文本进行保守修复。  
如果提示“模型输出缺少字段”或“仍包含模板痕迹”，通常是模型没有按 JSON 规则输出；Kimi 会按片段校验封面摘要和章节批次，遇到字符串未闭合、JSON 语法不完整或章节缺失时只补救重试当前片段，仍失败时可更换更强模型或重新生成。  
如果 Word 打开后目录页未显示页码，可在 Word 中右键目录并选择更新域。
